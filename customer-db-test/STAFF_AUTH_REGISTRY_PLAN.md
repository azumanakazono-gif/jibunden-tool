# じぶん電気｜スタッフ承認基盤（PR #318・検証専用）

## 現状
- Google Identity Services からの ID トークンはサーバー側で Google 公式ライブラリを使って検証する。
- `staff-approval-policy.mjs` は Google `sub` とサーバー所有の承認レコードを照合する純粋関数。
- `staff-registry-commands.mjs` は管理者承認済みの本人を要求し、登録・承認・停止・却下の状態遷移をモデル化する。実データの保存先にはまだ接続していない。
- `/api/staff-auth-preview` は引き続き認証成功後も HTTP 403 `STAFF_APPROVAL_NOT_IMPLEMENTED` を返す。**セッション発行・顧客DB接続・管理者APIは未実装。**
- 本番のコード・データ・アクセス制御にはこの変更を反映しない。

## 推奨するサーバー側保存モデル
**StaffRegistry**
- `googleSub`: Google の不変 subject ID、唯一キー。メールアドレスを認可キーにしない。
- `emailForDisplay`: 画面表示と管理者確認のためだけに使用（変更される可能性がある）。
- `status`: `pending | approved | suspended | rejected`
- `role`: `staff | admin`
- `version`: 競合防止用の整数
- `createdAt` / `updatedAt`: 日時
- 将来追加予定: 管理者の承認者 ID・承認日時・理由・利用停止理由。

**StaffAuditLog（追記専用）**
- `timestamp`, `actorSub`, `targetSub`, `action`, `fromStatus`, `toStatus`, `version`
- 変更前後を記録し、通常のスタッフが編集・削除できないこと。
- 顧客情報や ID トークン、ブラウザーのセッション秘密は監査ログへ保存しない。

## 保存先の必須条件
1. スタッフ台帳と監査ログはサーバー側でのみ読み書きする。ブラウザーから直接変更不可。
2. ユニーク `googleSub` を保証する。役割・状態はクライアントの入力値を信用しない。
3. 台帳の更新と監査ログ追加は同一の原子的トランザクションにする。失敗時はどちらもロールバック。
4. 複数管理者が同時に操作したときに競合状態を防ぐ。版番号の CAS または直列化可能なトランザクションが必要。
5. 初期管理者は **別途承認された安全なブートストラップ手順** で作成する。メール一致や初回ログインから管理者権限を自動発行しない。
6. スタッフは当初 `pending + staff` でのみ登録可能。管理者役割の付与・変更は別の承認設計とする。
7. ログイン済みセッションにも再検証・失効処理が必要。利用停止後に古いセッションが通らない設計をする。
8. API 実装時には CSRF、HttpOnly/Secure/SameSite Cookie、Origin 検証、ログイン・承認操作のレート制限を検証する。
9. 管理者画面・管理者 API を公開する前に、失敗パス・権限昇格・監査証跡・競合をテストする。
